# 知識 → 経験（概念を実装で掴む）

## 目的

「概念はなんとなく分かるが、このリポジトリではどう実装されているか見えない」というギャップを埋める。一般的なチュートリアルや教科書的な説明で終わらせず、**今読んでいるコード**に紐づけて、知識→経験の順で理解を固定する。

## いつ使うか

- 未知の用語・パターン・フレームワークの作法に遭遇して止まったとき
- 「これ何してるの」を、仕組みの理解まで踏み込みたいとき
- 新しいコードベースの構造やデータフローを掴みたいとき
- 理論（制御・数学・アルゴリズム等）は分かるが、周辺の実装慣習が不明なとき

**ROS2 固有の用語**（ノード、トピック、launch、colcon 等）が主題なら、併用で [ros2-onboard](../ros2-onboard/SKILL.md) を優先する。本スキルはドメインを問わない上位パターンを担当する。

**曖昧な詰まり**（「わからない」「動かない」だけ）なら、先に [wakaranai](../wakaranai/SKILL.md) で質問を具体化してから本スキルに戻る。

## 学習の原則

1. **知識が先、経験が後**。いきなりコードを追わせない。まず概念の骨格を一言で置いてから、実装に降りる。
2. **想像で語らない**。説明前に `Read` / `Grep` で対象コードと周辺を確認する。
3. **1回の説明は1概念＋関連1〜2個まで**。深追いしすぎない。学習効率は「理解→次へ」のテンポで決まる。
4. **既出は繰り返さない**。`.claude/notes/learning-log.md` を確認し、説明済みなら実例の追記か次の概念へ進む。

## 手順

### 0. 文脈を最小限だけ確認する

ユーザーが曖昧な場合のみ、**最大1〜2個**質問する（認知負荷を上げない）:

1. 今見ているファイル・関数はどこか
2. 何を理解したいか（用語の意味 / データの流れ / 書き換え方 など）

すでに発言に含まれていれば聞き直さない。

### 1. 知識（抽象）— 骨格を置く

コードを示す前に、短く:

- **定義**: 一言で何か
- **なぜここにあるか**: この文脈・このファイルでその概念が必要な理由
- **上位の関連**: 前提になる概念が1つあれば名前だけ示す（詳細は別回）

ここは **3〜5文以内**。教科書的な網羅説明はしない。

### 2. 経験（具体）— 実装に降りる

対象リポジトリのコードを確認したうえで:

- **実コード対応**: ファイルパス・関数・該当行を具体的に示す
- **動きの追い方**: 入力→処理→出力、呼び出し元/先、設定の流れなど、読む順序を1本の線で示す
- **周辺の確認ポイント**: 必要なら依存ファイル・設定・型定義・テストも `Read` して補足する

ドメインに応じて確認する典型例:

| 種類 | 見る場所の例 |
|------|-------------|
| パッケージ/モジュール構成 | `package.xml`, `pyproject.toml`, `CMakeLists.txt`, `setup.py` |
| 起動・配線 | launch ファイル, `main`, DI コンテナ, ルーティング定義 |
| データ契約 | メッセージ型, API スキーマ, 型定義, OpenAPI |
| 設定 | `.yaml`, `.env`, パラメータファイル, 環境変数 |
| ビルド・実行 | Makefile, CI, README の手順 |

### 3. 次の一手（経験を固定する）

説明の末尾に、ユーザーが **自分でやる1ステップ** を必ず1つ出す。例:

- 「`foo.cpp` の `bar()` から `baz()` への呼び出しを、手でトレースしてみる」
- 「`ros2 topic echo /...` で実際のメッセージを見る」
- 「この関数の引数を1つ変えて、テストを走らせる」

演習は小さく。完了できれば理解が経験に変わるサイズにする。

### 4. 学習ログに記録する

新しい概念を説明したら `.claude/notes/learning-log.md` に追記する（無ければ作成）:

```markdown
## <概念名>
- 定義: ...
- このリポジトリでの実例: `path/to/file` の `symbol()`（L行番号付近）
- 関連: ...
- 次の一手: ...
- 解説日: YYYY-MM-DD
```

同じ概念が既にあれば重複説明せず、新しい実例か「次の一手」だけ追記する。

## 回答フォーマット

毎回この骨格で返す:

```markdown
## 知識: <概念名>
[定義・なぜここにあるか・上位関連]

## 経験: このコードでの実装
[実コード対応・読む順序・周辺ファイル]

## 次の一手
[ユーザーが自分でやる1ステップ]
```

コード引用は Cursor のコード引用形式（`startLine:endLine:filepath`）を使う。

## 深さの調整

- ユーザーがドメインの理論（制御・数学・ML 等）に強く、**実装慣習・フレームワーク作法**に弱い前提で、初出の周辺用語は端折らない。
- `learning-log.md` に既出の概念は、同じ深さで繰り返さない。実例の差分だけ足す。
- ユーザーが「もっと深く」と言ったときだけ、関連概念を1つ追加で開く。

## やらないこと

- 知識フェーズを飛ばして、いきなり長いコードダンプを返さない。
- 1回の応答で概念を5個以上並べない。
- リポジトリを読まずに一般論だけを返さない。
- 次の一手なしで説明を終えない（経験に変換されない）。
- ユーザーがまだ何も書き出していない「わからない」に対して、本スキルで長い講義を始めない（wakaranai に委ねる）。

## 補助スキルとの役割分担

| スキル | 役割 |
|--------|------|
| **chi-keiken**（本スキル） | 概念→実装の理解。学習ログの蓄積 |
| **wakaranai** | 曖昧な詰まりの言語化。Q&A ログ |
| **ros2-onboard** | ROS2 固有の周辺知識と用語集 |
| **hanaseru** | 理解した内容を人に話す形への収束 |

理解が固まったあと、誰かに説明する必要があれば hanaseru に渡す。
