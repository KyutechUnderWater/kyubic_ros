# わからないを言語化する

## 目的
「なんとなくわからない」を、答えられる具体的な質問に変換する。これを1週間続けることで質問力そのものを鍛え、詰まりの記録をあとで見返せる資産にする。

## 手順

ユーザーが曖昧な訴え（例: 「わからない」「動かない」「これ何してるの」）をしてきたら、いきなり全部聞き出そうとせず、**最大1〜2個だけ**、最も情報量の多い質問を返す。優先順位:

1. 今見ているファイル・関数はどこか（わかれば十分。パスや名前だけでよい）
2. 期待していた動作と、実際に起きたこと（エラーメッセージ・出力・ログがあれば貼ってもらう）

すでにこの2つがユーザーの発言に含まれていれば聞き直さない。目的や「すでに試したこと」は無理に聞き出さず、回答の中で自然に補う。

## 回答の形式

情報が揃ったら、実際のコード（該当ファイル）を `Read`/`Grep` で確認したうえで回答する。回答には以下を含める:

- 今の理解の何が正しくて何がズレていたか（ズレがあれば明示する）
- 具体的な原因・仕組みの説明（実コードの該当箇所を示しながら）
- 次に確認すべきこと（あれば）

## ログの記録

回答が終わったら `.claude/notes/questions-log.md` に追記する（無ければ作成する）。誰が聞いたか後から分かるように、作業環境のWindowsユーザー名（作業ディレクトリのパス `C:\Users\<ユーザー名>\...` から取得、不明なら `whoami` / `$env:USERNAME` で確認）を必ず記録する:

```markdown
## Q: <ユーザーの質問を1行に要約>
- ユーザー: <Windowsユーザー名>
- 状況: <ファイル/関数>
- 期待 vs 実際: ...
- 回答要約: ...
- 日付: YYYY-MM-DD
```

これは締切前に見返すための、チームメンバー個々のFAQになる。同じ詰まりでも誰の記録かが分かることで、後から「これは誰の理解の穴か」を追跡できる。

## 注意
- 深追いしすぎて雑談にしない。1週間という制約があるので「詰まり → 言語化 → 解消 → 記録」のテンポを優先する。
- ユーザーが「わからない」しか言っていない状態で、質問を一度に何個も返さない。認知負荷になるのでNG。
- 同じような詰まりが `questions-log.md` に既にあれば、それを踏まえて回答する（車輪の再発明をしない）。
